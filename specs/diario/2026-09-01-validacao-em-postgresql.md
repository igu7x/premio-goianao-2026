# Validação em PostgreSQL de verdade

**Data.** 01/09/2026
**Motivo.** O sistema é desenvolvido sobre H2 em modo de compatibilidade
PostgreSQL. Isso reduz o atrito do dia a dia, mas *modo de compatibilidade não
é o banco*. Antes de subir para a infraestrutura do tribunal (GitLab +
OpenShift), era preciso provar que as migrações e o mapeamento JPA funcionam num
PostgreSQL real.

**Ambiente.** PostgreSQL 18.3 nativo no Windows (instalado por
`winget install PostgreSQL.PostgreSQL.16`, que na prática entregou o 18), base
`goianao`, perfil `postgres` com `--goianao.dados-demo=true`.

> A flag de dados de demonstração é necessária porque o perfil `postgres` tem
> `dados-demo: false` e **quem é administrador é uma linha na tabela
> `administrador`**. Sem a carga, o banco sobe vazio e ninguém tem papel de
> administrador — dá para logar, mas não para configurar nada.

---

## Resultado

**Migrações.** As 5 aplicadas, todas com `success = t` no
`flyway_schema_history`. Nenhuma incompatibilidade de dialeto. As restrições que
guiaram a escrita das migrações (sem índice parcial, sem `jsonb`,
`BIGINT GENERATED BY DEFAULT AS IDENTITY`, `VARCHAR` em vez de tipos
específicos) se pagaram: nada precisou ser ajustado.

**Esquema.** 8 tabelas de domínio criadas — `administrador`, `edicao`,
`unidade_judiciaria`, `magistrado_reconhecido`, `reconhecimento`,
`layout_certificado`, `servidor_habilitado`, `certificado_emitido`.

**Carga de demonstração.** 2 edições, 4 unidades, 6 magistrados, 10
reconhecimentos, 16 layouts, 33 servidores habilitados.

**Fluxo de ponta a ponta**, exercitado por HTTP contra o Postgres:

| Passo | Resultado |
|---|---|
| Login do administrador | JWT emitido, papéis resolvidos |
| `GET /api/painel/edicoes/1` | 8 layouts configurados, 0 pendências |
| Emissão pelo magistrado | PDF de 191 KB (`%PDF-1.6`), `X-Codigo-Validacao: 6AVJ-0ADK-BN2S` |
| `GET /api/public/certificados/{codigo}` sem login | `valido: true`, com nome, unidade, selo e data — **sem CPF** (007/RNF-2) |
| Reemissão da mesma combinação | **Mesmo código**; `total_emissoes = 2` na linha do banco |

A estabilidade do código entre reemissões e a contagem por certificado (não por
download) ficaram confirmadas em banco real, não só em teste.

## Pendências que isto revelou para o deploy

**1. Flyway anterior ao PostgreSQL 18.** O Flyway 11.7.2 avisa:

```
Flyway upgrade recommended: PostgreSQL 18.3 is newer than this version of
Flyway and support has not been tested. The latest supported version is 17.
```

É **aviso**, não erro — o método envolvido é
`recommendFlywayUpgradeIfNecessaryForMajorVersion`, e as migrações passaram.
Ainda assim, se o tribunal rodar PostgreSQL 18, subir a versão do Flyway antes é
mais barato que descobrir no cluster. **Falta confirmar com a infra qual versão
do PostgreSQL eles operam.**

**2. `goianao.storage.dir` grava em disco local.** As artes dos layouts vão para
`./data/artes`. Num pod isso não sobrevive ao restart: precisa de PVC ou de
object storage antes do deploy.

**3. `GOIANAO_JWT_SEGREDO` tem default no `application.yml`.** Serve ao
desenvolvimento; em produção tem que vir de Secret do OpenShift.

**4. Não existe containerização no repositório.** Sem `Dockerfile` (backend ou
frontend) e sem `.gitlab-ci.yml`. O `docker-compose.yml` só sobe o Postgres de
desenvolvimento — não empacota a aplicação.

## Nota de ambiente

O caminho com Docker não foi usado: o Docker Desktop instalou, mas o WSL não
está presente na máquina e o motor não sobe sem ele. Para validar o PostgreSQL
isso é indiferente — instalar o banco nativamente resolve. Para construir as
imagens do OpenShift, quem constrói costuma ser o runner do GitLab ou o próprio
cluster, não a máquina do desenvolvedor.
